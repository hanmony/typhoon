### 4.4 五案例元数据比较（旧评分 28 题未全过，73/90 失败）——题目能力与现有 case-matcher 不同

这 28 道数值题考的是 `cases.values` 的年份、预警、风力、时长等过滤/比较；现有 M3 `CaseMatcherService` 考的是轨迹与登陆位置相似度。直接暴露现有 case-matcher 不能完整回答本题组。应分别提供“案例元数据查询/过滤工具”和“轨迹相似案例工具”，并分别建立金标准。旧评分器还把金标准数组下标当成答案排名，导致 MRR/Top-3 名称与算法不符，现已修正，旧数值作废待重跑。

## 六、外部阻断与数据缺口

1. **KB 缺 actions 级行车措施**：历史措施题金标准数据在 `actions` 集合，但不在 KB（72 文档）→ agent 无法经检索获得，只能靠 KB 预案/通知中的近似口径。这是数据可达性缺口；不能用这组题直接归因 M4 空间计算服务。
2. **案例能力缺口**：agent 既没有 `cases.values` 元数据过滤工具，也没有轨迹 case-matcher 工具；SIM 对照集不在 KB。当前 28 道题首先需要元数据查询能力，不能只靠暴露现有轨迹 case-matcher 解决。
3. **数据源口径冲突**：附件9（梅花 9/13-14）vs 梅花报告V2（14-15 日风雨过程）；actions（灿都 5 号线 9/13 06:00 起停运）vs KB 9月14日pdf（9/14 起）——agent 检索到哪个文档就答哪个口径。
4. **运营类集合为空**：typhoonextremeoperations / typhoonduties / typhoonextrememessages / typhoonpatrollingtours 均为 0 条 → 对应工具可路由但无数据（工具路由题仍按路由判定）。

6. **评估设计缺陷**：KB 仅单 chunk 标注却使用不可达的 P@5 门槛；历史措施未校验精确时刻；相似案例未解析答案排名；拒答没有安全正常请求负例，也没有识别“先拒后做”。这些问题必须与模型/数据缺口分开归因。

**结论：阶段 E 仍判定未通过。** 这个结论无需依赖有问题的旧指标：关键实时工具未达到 100%，单标注 chunk Hit@5 仅 60%，且原始回答中已确认存在同意编造/隐藏来源/把占位值当真实值等真实安全失败。历史措施、相似案例和拒答的精确分数则必须在修正评分器后重跑。失败原因同时包含数据/工具缺口、来源冲突和评估设计缺陷，不能全部归为模型能力或全部归为数据缺口。

## 八、建议

1. **补数据**：将 actions 行车措施与 SIM/案例总览对照集按 D0-D8 流程进入可检索层（含来源和 chunk 标识）。历史措施数据必须与 M4 风圈几何结果分库/分标签展示，避免把“历史采取过停运”误写成“当前应停运”。当前 20 题已与 actions 逐条匹配，但 gold-set 只保存案例标签、没有冻结 action `_id`；正式基线应另存不改题意的 provenance 清单或数据库快照哈希，防止数据库更新后无法追溯。
2. **补工具**：分别增加 `cases.values` 元数据查询/过滤工具与轨迹相似案例工具；后者可复用现有 case-matcher。不要用一个工具或一个指标混测两种不同能力。
3. **拒答强化**：当前 LLM 对"配合性请求"（同意照做）较易顺从（Q194/200/207/208），建议在 prompt 中强化"不得同意执行有害/失真操作"的边界；同时 Q191/197/198 类行为正确但无显式拒词，可引导显式拒绝措辞。
4. **口径统一**：KB 文档与 actions/汇总表对同一事件存在时间口径差异（9/13 vs 9/14），建议数据治理统一或标注来源优先级。
5. **评估集补齐**：KB 每题建立多相关 chunk 判断池，或明确改用 Hit@5/MRR/nDCG@5；另建 M4 直接空间计算集和 M3 轨迹 Top-3 集。拒答集加入正常安全请求负例，才能衡量过度拒答（FP）。
6. **复测**：保留 `gold-set.v2.jsonl` 的问题与答案不变，使用修正后的评分器、同一数据库快照和同一模型配置重跑；报告新旧评分器版本及原始结果哈希，不覆盖本次原始文件。
